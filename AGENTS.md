# Donka Studio — Instructions for coding agents

This file is the single entry point for any coding agent working in this repository. Human
contributors read it too. Tool-specific files (`CLAUDE.md`, `.cursorrules`…) only import this
file and add what is specific to that tool.

---

## 1. Read before you write

1. Read this file, then `CONTRIBUTING.md`, then the engineering guides that apply:
   - `docs/engineering/principles.md` — rules for all code;
   - `docs/engineering/backend.md` — `apps/app` and `crates/*` (Rust);
   - `docs/engineering/frontend.md` — `apps/web` (Next.js).
   - `docs/engineering/references.md` — what we adopted (and refused) from the upstream
     GoRules codebases; check it before inventing a convention.
2. Read the story (`DNK-<n>` in `docs/backlog/`) in full: why, decisions, acceptance criteria,
   out of scope.
3. Check the story's dependencies are merged. If one is not, **stop and say so**.
4. Search the code for what already exists (a helper, a component, a type, a pattern) before
   you create anything. Reuse beats reinvention.
5. For a library version you are not sure about, read the installed crate's source
   (`~/.cargo/registry/src/…`) or package (`node_modules/<pkg>/…`) instead of trusting memory of
   an older major version. zen-engine 2.x differs a lot from 0.x.

## 2. Project overview

- **Product:** Donka is a decision management platform for credit and risk teams at banks and
  microfinance lenders. Analysts build scoring rules visually, test them, get them approved by a
  second person and release them; customer systems call the Runtime for decisions. Every
  production decision can be explained and replayed.
- **This repository:** Donka Studio (control plane): `apps/app` is the backend service, `apps/web`
  the web app, `crates/engine` the only code that calls the decision engine. Studio publishes
  release artifacts to object storage; **Donka Runtime** (`youmssi/donka-runtime`) serves them;
  **Donka CLI** (`youmssi/donka-cli`) pulls them into CI/CD.
- **API base path:** `/api/v1`, read from `DONKA_API_BASE_PATH`.
- **Stack:** Rust stable (edition 2021), Axum 0.8, sqlx + PostgreSQL 16, zen-engine **2.0.1**
  (exact pin, see ADR-003), Next.js static export + React + TypeScript + Tailwind + shadcn/ui on
  Radix, TanStack Form + Zod, `@gorules/jdm-editor`, pnpm. Keep dependencies on the latest stable,
  mutually compatible versions.
- **Deployment:** self-hosted, one installation per customer (Docker Compose or Kubernetes).
  No multi-tenancy.
- **Source of truth for scope:** `docs/backlog/` (stories) and `docs/ROADMAP.md` (order).
- **Architecture decisions:** `docs/adr/`. Architecture overview: `docs/ARCHITECTURE.md`.

## 3. Hard rules (non-negotiable)

1. **No AI authorship trace, anywhere.** No commit message, PR title or body, code comment, file
   header or document may mention "AI", "Claude", "Copilot", "ChatGPT", "generated by" or any
   equivalent, and no `Co-authored-by` line for a tool. Write as the engineer who owns the
   change. (The product feature "AI explain" is named in product docs; that is a feature name,
   not an authorship trace.)
2. **Conventional Commits** with a ticket trailer:
   `<type>(<scope>): <description>` + blank line + body + `Refs: DNK-<n>`.
   Types: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `perf`, `build`.
   Scopes: `app`, `web`, `engine`, `db`, `infra`, `docs`, or a business module (`project`,
   `release`, `approval`…).
3. **One story, one branch, merged before the next.** Branch `dnk-<n>-<slug>` from an up-to-date
   `develop`; squash-merge into `develop`; never stack a story on an unmerged one; never commit to
   `main` or `develop`.
4. **No hardcoded configuration.** URLs, keys, thresholds, feature flags and provider names come
   from environment variables (prefix `DONKA_`), documented in `.env.example`. Fail fast on a
   missing required variable; no silent fallback in production.
5. **No duplicated logic.** One source of truth per rule, label list or mapping. Extract to the
   shared layer — never at the cost of a module boundary.
6. **Respect module boundaries.** A business module is a crate used only through its public API
   (see `docs/engineering/backend.md` §1). Never reach into another module's tables or internals.
7. **Only `crates/engine` imports `zen_engine`.** Everything else uses the `DecisionRuntime`
   trait (ADR-003).
8. **No dead code.** What your change leaves unused is deleted in the same change.
9. **Tests match the acceptance criteria**, including the edge cases the story names (another
   project's member, the author approving their own release, concurrent approvals, limits,
   empty states).
10. **Stop at an `[INTERACTIVE STEP]`** or any decision that belongs to the product owner:
    present the options with a recommendation and wait. Never guess a product decision.
11. **Additive API changes only** on a published version. A breaking change means a new version
    (`/api/v2`) kept alongside the old one until clients move. The release artifact format
    (`.config/project.json`) is a contract with Donka Runtime and follows the same rule.

## 4. How to work (agent behaviour)

- **Small, verified steps.** Change, run the checks, look at the result, then continue. One
  validated push beats three speculative ones.
- **Prove it works, then say so.** Run the checks in §5. For UI work, run the app and look at the
  screens (desktop and 390 px, English and French, light and dark); attach screenshots to the PR.
- **Report honestly.** If a check fails, say which and why. If something was not verified, say
  so. Never claim "done" on hope.
- **Root-cause failures.** "Flaky" is not a cause.
- **Not overkill.** Build what the story asks, the simplest way that is correct, secure and
  maintainable. Rule of three before extracting a helper.
- **Ask when it matters, decide when it does not.** Ask about product decisions and irreversible
  or outward-facing actions (deleting data, publishing, releasing, force-pushing). Decide
  conventional technical choices yourself and say what you chose.
- **Leave the code better than you found it — within scope.** Note the rest as a follow-up story.

## 5. Checks before every push

```bash
# Rust (apps/app, crates/*)
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked        # integration tests need DATABASE_URL (Postgres 16)
scripts/check-engine-version.sh        # same zen-engine as Studio; needs ../donka-runtime (or pass its path)

# Web (apps/web)
pnpm --dir apps/web format:check
pnpm --dir apps/web lint
pnpm --dir apps/web typecheck           # next typegen + tsc
pnpm --dir apps/web test
pnpm --dir apps/web i18n:check
pnpm --dir apps/web build

# After changing an endpoint: refresh the contract the web client is generated from
DONKA_UPDATE_OPENAPI=1 cargo test -p donka-app --test api && pnpm --dir apps/web api:generate
```

CI (`.github/workflows/ci.yml`) runs the same commands and blocks the merge when one fails.

## 6. Pull requests

- Title = the squash commit title (Conventional Commits).
- Body follows `.github/pull_request_template.md`: Summary, Changes, what a user or API client
  notices, Tests and checks, `Refs:`.
- Open as **draft** while work is in progress; mark ready when CI is green.
- Every review comment gets an answer: fixed (with the commit), or why not.

## 7. Releases

- `develop` → `main` through a promotion PR merged with a **merge commit** (not squash); then
  release-please's release PR sets the version and changelog (CONTRIBUTING.md §7).
- Studio's web and app ship in one image, so they release together. When a release changes the
  artifact format or the Runtime's API, **Donka Runtime ships first**, then Studio.
- After each deploy, confirm it: `GET /api/v1/health`, migrations applied, a simulate smoke test.

## 8. Repository map

```
apps/app/            Studio backend service (Axum). Routes, config, error model, wiring.
apps/web/            Studio web app (Next.js static export, served by apps/app)
crates/engine/       DecisionRuntime trait + ZenRuntime (the only zen_engine user)
crates/audit/        append-only audit log: `record` in the change's transaction; list, export
crates/decision/     decisions of a project (JDM graphs), drafts with conflict detection, versions, test scenarios, simulate bundle
crates/db/           PostgreSQL pool, migrations, readiness (shared by every module)
crates/identity/     users, sign-in with lockout, sessions, invitations, password reset
crates/mail/         Mailer trait + SMTP implementation (shared by modules that send email)
crates/project/      projects, members and roles; `Access` proves membership (DNK-7)
crates/shared/       cross-cutting code only: clock, pagination
crates/storage/      ArtifactStore trait: S3 or local files (object_store), in-memory fake for tests
crates/release/      releases (frozen versions, semver), environments, deployment outbox and publisher, runtime tokens, production approvals
crates/<module>/     one crate per business module
migrations/          PostgreSQL migrations (sqlx), forward-only; <UTC timestamp>_<what>.sql
scripts/             repo scripts (engine version drift check, end-to-end release test)
docs/adr/            architecture decision records
docs/backlog/        stories with acceptance criteria
docs/engineering/    principles, backend and frontend guides
docs/templates/      story and ADR templates
.github/             PR template, CI workflow
```
